# Hardware and approach

## The board (Psikyo PS5, MAME `psikyo/psikyosh.cpp`, machine `psikyo5`)

| Part | Details | Implementation |
|---|---|---|
| CPU | Hitachi SH7604 (SH-2), 28.63635 MHz (57.2727 MHz / 2) | translated program + `runtime/src/sh2_*.c` |
| Program ROM | 1 MiB at 0x00000000 (two 512 KiB ROMs, 32-bit word-swapped interleave) | translated |
| Program in RAM | the boot code (reset at 0x400) copies 0x2D9C0 bytes of the program to 0x06000000 and runs it there; the copy descriptor is read from the ROM at translation time | translated at its RAM address |
| Data ROM window | 0x05000000-0x0507FFFF (empty on this board, reads 0) | `board.c` |
| Work RAM | 1 MiB at 0x06000000 | `board.c` |
| Inputs | 0x03000000 (players, coins, service, debug switch), 0x03000004 (JP4 region jumpers, EEPROM DO in bit 28) | `board.c` |
| EEPROM | 93C56 in 8-bit mode (256 bytes); DI / CLK / CS on byte writes to 0x03000004 (bits 5 / 6 / 7); default contents from `eeprom-dragnblz.u44` | `eeprom.c`, persisted by the frontend |
| Sound | Yamaha YMF278B (OPL4) at 28.63635 MHz, 0x03100000-07, 2 MiB of wave ROM; 6 outputs summed to one mono speaker; IRQ to SH-2 level 12 | ymfm via `ymf278b.cpp` |
| Video | PS6406B: sprite/background RAM 0x04000000 (64 KiB, 32 banks of 2 KiB), palette 0x04040000 (5,120 RGBx_888 entries), sprite zoom table 0x04050000, video registers 0x0405FFE0, graphics-ROM test window 0x04060000 | `video.c` |
| Graphics ROM | 44 MiB region (20 ROMs of 2 MiB from 4 MiB, 16x16 tiles in 4 or 8 bpp) | read from your zip at run time |
| Interrupts | IRQ 4 asserted at the start of VBLANK, held until the game writes 0x0405FFDC with bits 22-23 clear; YMF278B timer IRQ on level 12 (held while the chip asserts it); SH7604 FRT/DIVU | `board.c` |
| Screen | 320x224 visible of a 512x256 raster, 60 Hz, monitor rotated (ROT270) | frontend |

### Video (PS6406B)

Ported from MAME's `psikyosh_v.cpp`, including the parts of MAME's
`drawgfx.cpp` it relies on, and computing the same ARGB intermediate values so
the result can be compared pixel for pixel:

- Each frame starts with a per-line fill colour (line fill bank), then for
  priorities 0-7: sprites, the four background layers, and an optional
  per-line blend.
- Sprites: up to 1,024 in a list latched at VBLANK; 1-16 x 1-16 tiles, 4 or
  8 bpp, zoom through a 256-entry lookup table, flip, eight alpha settings
  (fixed alpha or per-pen alpha for pens 0xC0-0xFF), a Z-buffer that keeps
  sprite-sprite order, and a priority mapping per sprite group.
- Backgrounds: up to four 32x16 or 32x32 tile layers. Normal layers have one
  scroll/alpha/bank setting; "line" layers take scroll, zoom, alpha, priority
  and tile bank per scanline (used for the warping and fading effects).
- As in MAME the picture is drawn at the start of VBLANK, before the new
  sprite list is latched, so sprites appear one frame after they are written.

### Sound (YMF278B)

The chip is the ymfm library (BSD-3-Clause), the same code MAME 0.264 uses.
`runtime/src/ymf278b.cpp` provides what MAME's `ymfm_device_base` /
`ymf278b_device` provide: the stream rate (clock / 768 = 37,286 Hz), timers
and the busy flag on the board clock, the IRQ line, and PCM reads from the
wave ROM. Samples are generated exactly up to the time of each chip access,
with MAME's per-second sample indexing, so the chip's "load" and "busy"
status bits change on the same CPU cycle as in MAME.

## Translator

`tools/sh2dec.py` decodes SH-2 opcodes following MAME's `execute_one`.
`tools/recompilesh2.py` walks the code from the vector table, the RAM copy of
the program, seeds, literal-pool code pointers (iterated to a fixed point) and
pointer tables, keeps only plausible entry points, and emits one C function per
instruction plus a hashed dispatch table.

- Delayed branches run their delay slot inline.
- Cycles are counted exactly as MAME's SH-2 interpreter does, and in the same
  order: an instruction's extra cycles inside it, its base cycle afterwards. A
  memory access therefore sees the same CPU time as in MAME, which matters for
  the EEPROM's ready line and the sound chip's status bits.
- Interrupts are taken between instructions, where MAME's interpreter takes
  them (when a line is raised, after SR changes and after RTE).
- **RAM code.** The translated functions for the RAM copy of the program are
  only used while the RAM still holds exactly the bytes they were translated
  from: the board counts, per 4 KiB page, the words that differ from the ROM
  source, and any code in a page that differs (before the copy, or if the game
  ever modified it) runs on the interpreter. In practice the copy is never
  modified after boot.

The fallback interpreter (`runtime/src/sh2_interp.c`, generated by
`tools/make_sh2_interp.py`) is a 65,536-entry decode table over the same
semantic functions, with the same cycle and delay-slot rules. The recompiled
and generic builds produce identical per-frame RAM hashes, so the translator
and the interpreter cross-check each other.

## Timing model

MAME keeps time in attoseconds; the board does the same arithmetic in CPU
cycles: a frame is 10^18/60 attoseconds, a cycle 10^18/28,636,350 (both
truncated as in MAME), and the CPU stops at the first instruction boundary at
or after floor(VBLANK time / cycle time). The screen starts in VBLANK at time 0
and VBLANK begins every 1/60 s. The game measures its idle time in a counter
that seeds its random number generator, so this level of agreement is what
keeps gameplay identical to MAME.

## How it was verified

Against MAME 0.264 running the same ROM (`-nodrc`, i.e. MAME's SH-2
interpreter; fresh NVRAM; references made locally, not distributed):

- **Attract mode:** work RAM (1 MiB) byte-identical and the screen
  pixel-identical at frames 60, 120, 300, 600, 900, 1,200, 1,500, 1,800,
  2,400, 3,000 and 3,600 (monitor-adjust screen, title, demo play, rankings).
- **Gameplay:** a scripted one-player game (coin at frame 1,500, start, then
  moving, shooting and bombing; `--inputs demo` here,
  `tools/mame/demo_inputs.lua` in MAME): work RAM and screen identical at
  frames 1,800, 2,400, 3,000, 3,600, 4,200 and 4,800. Two values watched every
  frame (the idle counter and the random seed) match at all 4,800 frames.
- **Audio:** MAME's `-wavwrite -nocompressor` recording of the same 80 s
  scripted run vs ours: per-second RMS level within ±1.5 % (mostly 0.3-0.8 %),
  waveform correlation 0.996 after resampling ours to MAME's 48 kHz output
  (MAME resamples, so sample-exact comparison is not possible).
- **Translator vs interpreter:** recompiled and generic builds produce
  identical per-frame RAM hashes over 20,000 frames of random play.
